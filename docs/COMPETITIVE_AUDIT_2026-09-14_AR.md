# مراجعة تنافسية وخطة تقوية طلباتك — 2026-09-14

## الهدف
رفع جودة تطبيق «طلباتك» بدون التضحية بالاستقرار أو الأمان، مع الحفاظ على سياسة الاعتماد على خدمات مجانية قدر الإمكان.

## قاعدة التطوير الجديدة
أي إصلاح أو ميزة جديدة لا تعتبر جاهزة للإنتاج إلا بعد مرورها على CI كامل: doctor + lint + typecheck + unit/regression tests + live backend/auth smoke + web export + Playwright E2E. نشر Web وOTA وبناء APK يجب أن يكون خلف بوابة تحقق، وأي عطل يتم اكتشافه يدويًا يتحول إلى regression test قبل إغلاقه.

## نقاط القوة الحالية
- تسجيل ودخول برقم الهاتف + كلمة مرور مع فصل أدوار customer/merchant/driver/admin.
- موافقة إدارية للتاجر والمندوب، والعميل يدخل مباشرة.
- RLS/RBAC وعمليات حساسة عبر RPCs/Backend.
- طلبات متعددة المتاجر مع تقسيم آمن ومنع التكرار عبر request id.
- طلبات مجدولة.
- عناوين متعددة + تحديد موقع على الخريطة.
- مفضلة، تقييم متجر ومندوب، إعادة طلب، تتبع مباشر للمندوب.
- إشعارات، شكاوى، ملف شخصي بصورة وتفضيلات توصيل.
- PWA + Android + OTA + لوحة إدارة + تقارير تاجر.
- تحديثات وإصدارات محمية باختبارات آلية.

## أهم الفجوات التي ظهرت في المراجعة
1. البحث في الصفحة الرئيسية يبحث في المتاجر فقط؛ لا يوجد بحث موحد على مستوى الأطباق والمنتجات.
2. لا يوجد شات حي بين العميل والمندوب أو العميل والدعم داخل الطلب.
3. مركز الدعم يعتمد على تذاكر/شكاوى وليس محادثة فورية أو حل ذاتي ذكي.
4. صفحة الإشعارات لا تفتح مباشرةً الطلب/المتجر المرتبط بالإشعار.
5. لا يوجد Loyalty/Points/Referral فعال للمستخدمين.
6. لا يوجد Home personalization حقيقي مبني على الطلبات السابقة، المفضلة، الوقت، والموقع.
7. لا يوجد ETA ذكي واضح يجمع وقت تجهيز التاجر + استلام المندوب + المسافة.
8. لا يوجد Order issue flow مخصص: ناقص/خطأ/تأخير/تالف مع خطوات حل واضحة.
9. E2E الحالي يركز على Web/public flows أكثر من Android-native؛ الاختبارات الأصلية على جهاز Android تحتاج تقوية تدريجية.
10. authenticated backend smoke يعتمد على بيانات اختبار سرية اختيارية؛ يلزم حساب Customer اختبار مخصص غير إداري حتى لا يتم تخطي الجزء المصادق عليه من الفحص.

## ما نتعلمه من المنافسين
### Talabat
- التحول إلى everyday app متعدد الفئات: طعام، بقالة، صيدليات، ورد وغيرها.
- اشتراك ولاء/توصيل مجاني ومكافآت لزيادة تكرار الطلب.
- وضوح الرسوم قبل الدفع.

### Rabbit
- السرعة والوضوح كميزة رئيسية.
- تجربة شراء قصيرة جدًا، تشكيلة كبيرة، اشتراك شهري ومزايا أعضاء.

### elmenus
- الاكتشاف بالطبق والصورة والتقييم وليس باسم المطعم فقط.
- محتوى بصري يساعد المستخدم يقرر يأكل إيه.

### Mrsool
- محادثة مباشرة مع المندوب.
- مرونة «اطلب أي شيء» وإضافة عناصر/أماكن متعددة.

## الأولويات المقترحة
### P0 — قبل أي توسع كبير
- إكمال تثبيت الخريطة وOTA على Build 11 واختبارهما يدويًا على Android.
- إنشاء حساب Customer اختبار مخصص وتشغيل authenticated backend smoke دائمًا.
- إضافة deep links للإشعارات.
- إضافة اختبارات Native للخرائط، اختيار الصور، foreground/background، والعودة بعد OTA.

### P1 — أعلى قيمة للمستخدم
- Unified Search: بحث في المتاجر + المنتجات + الأطباق مع فلاتر السعر/التقييم/الوقت.
- Quick Reorder على الصفحة الرئيسية «اطلب تاني» بدون الدخول لسجل الطلبات.
- «طلباتي المعتادة» و«قريب منك» و«مفتوح الآن» بترتيب شخصي بسيط من بيانات المستخدم نفسه.
- Order Issue Center لكل طلب مع أنواع مشكلة وخطوات حل.
- شات داخل الطلب مع المندوب، ثم دعم مباشر.
- ETA أكثر دقة مع آخر تحديث واضح.

### P2 — نمو واحتفاظ
- نظام نقاط ومكافآت بسيط ومحكوم من السيرفر.
- Referral codes بدون خصم مالي في البداية: شارات/نقاط/مزايا غير نقدية حتى نقرر الاقتصاد المناسب.
- عروض المتاجر الممولة/المميزة من لوحة الإدارة.
- Collections موسمية: فطار، سحور، عزومات، قهوة، حلويات، إلخ.

### P3 — التميز
- مساعد «طلباتك AI» داخل التطبيق.
- بحث بالمحادثة: «عايز حاجة حلوة تحت 150 جنيه وتوصل بسرعة».
- اقتراح وجبات من المتاجر المتاحة فعليًا.
- تتبع الطلب والاستفسار عن حالته عبر المحادثة.
- فتح شكوى/مشكلة من الشات بعد تأكيد المستخدم.

## تصميم الشات بوت المقترح
اسم مبدئي: «مساعد طلباتك».

### المبدأ الأمني
المساعد لا يحصل على Service Role ولا ينفذ SQL مباشر. كل قراءة/تنفيذ يتم من خلال RPCs أو APIs محددة ومقيدة بـ auth.uid() وRLS. أي Action حساس مثل إلغاء الطلب أو إرسال شكوى أو تعديل عنوان يتطلب تأكيد واضح من المستخدم قبل التنفيذ.

### MVP مجاني وقابل للتوسع
المرحلة الأولى لا تحتاج API ذكاء مدفوع:
- Intent Router محلي/Edge Function: search_products, search_stores, order_status, reorder, support, faq.
- قراءة Catalog/Orders من Supabase عبر وظائف آمنة.
- Replies قالبية بالعربية المصرية.
- سجل محادثة قصير مرتبط بالمستخدم مع سياسة احتفاظ واضحة.
- Rate limiting لمنع الإساءة.

ثم نضيف Provider abstraction بحيث يمكن توصيل نموذج AI مجاني/مدفوع لاحقًا بدون تغيير باقي التطبيق.

### أمثلة أوامر مفيدة
- «عايز برجر أقل من 200 جنيه» → بحث منتجات فعلي.
- «فين طلبي؟» → حالة الطلب الحالي + ETA.
- «اطلب آخر حاجة طلبتها» → يعرض الطلب ويطلب تأكيد قبل الإرسال.
- «الطلب ناقص» → يبدأ issue flow ويجمع التفاصيل.
- «اقترحلي حاجة خفيفة» → يعتمد على الكتالوج المتاح والتفضيلات.

## مؤشرات نجاح نقيسها
- crash-free sessions.
- نسبة نجاح إنشاء الطلب.
- الوقت من فتح التطبيق حتى تأكيد الطلب.
- repeat-order rate.
- search-to-cart conversion.
- نسبة الشكاوى لكل 100 طلب.
- زمن حل الشكوى.
- delivery ETA accuracy.
- نسبة فشل/تراجع كل إصدار بعد النشر.

## قرار تنفيذي
لا نبدأ إضافة عشرات المزايا مرة واحدة. أولًا نثبت Android/Map/OTA ونقفل بوابات الإصدار، ثم ننفذ Unified Search + Deep Links + Order Issue Center + In-order Chat، وبعدها نبني مساعد «طلباتك AI» فوق البيانات والوظائف المستقرة.
